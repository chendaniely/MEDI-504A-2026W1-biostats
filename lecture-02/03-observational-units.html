The original third rule

The original definition from the 2014 Tidy Data paper is:

  1. Each variable forms a column
  2. Each observation forms a row
  3. Each type of observational unit forms a table

An observational unit is the kind of thing you’re observing, for example a song, a patient, or a hospital visit. The third rule says different kinds of things belong in different tables.

Problem 4: multiple observational units

Our tidy Billboard table still mixes two kinds of things. The song information (year, artist, track, time) is repeated on every row, for every week the song was on the chart. We can split it into two tables that share an id column.

  distinct(artist, track, year, time) |>
  mutate(id = row_number(), .before = 1)

Problem 5: one unit in many tables

The opposite problem is one kind of observation split across many files, such as one file per year or one per hospital site. If the files have the same columns, we can stack them with bind_rows() or give read_csv() all the file names at once.

How hospitals store data

Hospital databases follow the paper’s third rule, with one table per kind of observational unit, linked by ID columns.

  • patients has one row per patient
  • encounters has one row per visit, with the patient’s ID
  • conditions, medications, and observations have one row per record, with the patient and encounter IDs

To analyze the data, we join the tables we need into one tidy table.

Synthea creates fake but realistic patient records stored this way. Its downloads page has samples of 100 patients in CSV, HL7 FHIR, and C-CDA formats.

Beyond CSVs: health data standards

In practice, health data is usually stored and shared using data standards, not as a folder of CSV files.

  • HL7 is the family of standards hospital systems use to exchange clinical data
  • FHIR (Fast Healthcare Interoperability Resources) is HL7’s newer standard, which sends a patient, an encounter, or an observation as a “resource” through web APIs
  • The OMOP Common Data Model, from the OHDSI community, is a shared database layout for observational health data, so the same analysis code can run on many hospitals’ databases

All of these follow the third rule, with one table (or resource) per kind of observational unit, linked by IDs.
