Observational units

Packages

library(tidyverse)

The original third rule

The original definition from the 2014 Tidy Data paper is:

  1. Each variable forms a column
  2. Each observation forms a row
  3. Each type of observational unit forms a table

An observational unit is the kind of thing you’re observing, for example a song, a patient, or a hospital visit. The third rule says different kinds of things belong in different tables.

Problem 5: one unit in many tables

The opposite problem is one kind of observation split across many files, such as one file per year or one per hospital site. If the files have the same columns, we can stack them with bind_rows() or give read_csv() all the file names at once.

How hospitals store data

Hospital databases follow the paper’s third rule, with one table per kind of observational unit, linked by ID columns.

  • patients has one row per patient
  • encounters has one row per visit, with the patient’s ID
  • conditions, medications, and observations have one row per record, with the patient and encounter IDs

To analyze the data, we join the tables we need into one tidy table.

Synthea creates fake but realistic patient records stored this way. Its downloads page has samples of 100 patients in CSV, HL7 FHIR, and C-CDA formats.

Beyond CSVs: health data standards

In practice, health data is usually stored and shared using data standards, not as a folder of CSV files.

  • HL7 is the family of standards hospital systems use to exchange clinical data
  • FHIR (Fast Healthcare Interoperability Resources) is HL7’s newer standard, which sends a patient, an encounter, or an observation as a “resource” through web APIs
  • The OMOP Common Data Model, from the OHDSI community, is a shared database layout for observational health data, so the same analysis code can run on many hospitals’ databases

All of these follow the third rule, with one table (or resource) per kind of observational unit, linked by IDs.

Back to Sacramento

On Monday we fit price ~ sqft on the Sacramento house sales. Let’s add type, a categorical variable, so we can see how to read both kinds of variables.

Sacramento |>

  type             n
  <fct>        <int>
1 Condo           53
2 Multi_Family    13
3 Residential    866

Dummy variables

  • A regression needs numbers, so R turns a categorical variable (a factor) into dummy variables, also called indicator variables
  • Each dummy variable is a 0/1 column for one level, and there’s one for every level except the first
  • The level without a column is the reference level, and every other level gets compared with it

Two names for the same idea

  • Statistics calls this dummy variable encoding
  • Computer science and machine learning call it one-hot encoding
  • Both turn each level of a categorical variable into a 0/1 column
  • One-hot encoding usually keeps a column for every level, while a regression with an intercept drops one, the reference level (R does this for us)

type as dummy variables

type has 3 levels, so it becomes 2 dummy variables, with Condo as the reference:

type typeMulti_Family typeResidential
Condo 0 0
Multi_Family 1 0
Residential 0 1

Interpreting a continuous variable

For every 1 [unit] increase in [variable], we expect [outcome] to increase (or decrease) by [estimate] [units], all else remaining the same.

For sqft:

For every 1 square foot increase in size, we expect the sale price to increase by $139, all else remaining the same (95% CI: $131 to $146).

  • “All else remaining the same” means the other variables in the model, so here, a house of the same type

Interpreting a categorical variable

We expect [outcome] for [level] to be [estimate] [units] higher (or lower) than for [reference level], all else remaining the same.

For typeMulti_Family:

We expect multi-family homes to sell for $66,224 less than condos, all else remaining the same (95% CI: $14,762 to $117,686 less).

  • Here “all else” is the size: a multi-family home and a condo with the same square footage
  • The comparison is always with the reference level, Condo

When the interval includes 0

For typeResidential:

We expect residential homes to sell for $8,253 more than condos, all else remaining the same (95% CI: -$15,594 to $32,100).

  • The interval includes 0, so the data don’t show a clear difference between residential homes and condos of the same size
  • We still report the estimate and its interval, and say that it’s unclear

The intercept

  • The intercept is the expected outcome when every continuous variable is 0 and every categorical variable is at its reference level
  • Here that’s a condo with 0 square feet, which doesn’t exist, so we don’t interpret it

A sore throat after surgery

licorice_gargle (from medicaldata) is a trial of 235 adults having thoracic surgery with a large breathing tube. Before the tube went in, they were randomized to gargle licorice or sugar water. Our outcome is any sore throat 30 minutes after surgery.

Recode the variables

sore <- licorice_gargle |>
  mutate(
    sore_throat = factor(pacu30min_throatPain > 0,
                         levels = c(FALSE, TRUE),
                         labels = c("no", "yes")),
    treatment = factor(treat, levels = c(0, 1),
                       labels = c("sugar", "licorice")),
    smoking = factor(preOp_smoking, levels = c(3, 2, 1),
                     labels = c("never", "past",
                                "current"))
  ) |>
  select(sore_throat, treatment,
         bmi = preOp_calcBMI, smoking) |>
  drop_na()

Which level are we modelling?

  • logistic_reg() models the odds of the outcome’s second level
  • sore_throat has the levels no, then yes, so every result is about the odds of a sore throat
  • The predictors are a mix of both kinds:
    • treatment: 2 levels, so 1 dummy variable (reference sugar)
    • bmi: continuous, in kg/m²
    • smoking: 3 levels, so 2 dummy variables (reference never)
count(sore, sore_throat)
  sore_throat   n
1          no 169
2         yes  64

Fit the model

sore_fit <- logistic_reg() |>
  fit(sore_throat ~ treatment + bmi + smoking,
      data = sore)

  • An odds ratio of 1 means no difference, below 1 means lower odds, and above 1 means higher odds

Interpreting a continuous variable

For every 1 [unit] increase in [variable], we expect the odds of [outcome] to be multiplied by [odds ratio], all else remaining the same.

For bmi:

For every 1 kg/m² increase in BMI, we expect the odds of a sore throat to be multiplied by 0.95, all else remaining the same (95% CI: 0.88 to 1.02).

  • Multiplied by 0.95 is the same as 5% lower odds
  • The interval includes 1, so the data don’t show a clear effect of BMI

Interpreting a categorical variable

We expect the odds of [outcome] for [level] to be [odds ratio] times the odds for [reference level], all else remaining the same.

For treatmentlicorice:

We expect the odds of a sore throat for patients who gargled licorice to be 0.38 times the odds for patients who gargled sugar water, all else remaining the same (95% CI: 0.20 to 0.71).

  • That’s 62% lower odds, and the interval doesn’t include 1

A categorical variable with more levels

Each dummy variable compares one level with the reference, never. For smokingpast:

We expect the odds of a sore throat for past smokers to be 4.38 times the odds for people who never smoked, all else remaining the same (95% CI: 1.94 to 10.48).

  • smokingcurrent compares current smokers with people who never smoked, not with past smokers
  • Its interval (0.86 to 4.33) includes 1, so that comparison isn’t clear

Odds, not probability

  • An odds ratio compares odds, not probabilities
  • Say “0.38 times the odds”, not “0.38 times as likely” or “62% less likely”
  • The two are close only when the outcome is rare, and here 27% of patients had a sore throat

The same model in base R

Base R’s glm() fits the same model with less code:

glm(sore_throat ~ treatment + bmi + smoking,
    family = binomial, data = sore) |>
  tidy(exponentiate = TRUE, conf.int = TRUE)
